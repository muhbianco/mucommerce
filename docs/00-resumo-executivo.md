# A. Resumo executivo e análise crítica do escopo

## 1. Análise crítica do escopo (o que o pedido assume e o que a realidade do hel1 impõe)

Cada item abaixo muda uma decisão de desenho. Fonte: inventário da VPS (18/09/2026), código da `api-agents`, repo `muh_chatwoot`, docs públicas dos provedores.

| # | Achado | Consequência no desenho |
|---|--------|-------------------------|
| 1 | **"InfiPay" é a InfinitePay (CloudWalk).** A API pública é **checkout hospedado** (`POST https://api.checkout.infinitepay.io/links`, identificado só pelo `handle`/InfiniteTag, sem API key), webhook **sem assinatura** publicada, confirmação por `POST /payment_check`, **sem API de estorno**. | "Checkout transparente" só existe com Mercado Pago. A abstração `PaymentProvider` precisa de dois fluxos: `embedded` (MP Bricks: Pix QR e token de cartão na nossa página) e `redirect` (InfinitePay). Webhook InfinitePay é **não confiável até** `payment_check` confirmar `order_nsu`, `amount` e `transaction_nsu`. Estorno InfinitePay = manual no app, registrado como `refund.method=external`. |
| 2 | **Mercado Pago**: `POST /v1/payments` exige `X-Idempotency-Key`; webhook assina `x-signature` (HMAC-SHA256 de `id:{data.id};request-id:{x-request-id};ts:{ts};`); depois é obrigatório `GET /v1/payments/{id}`. A `api-agents` hoje usa **Checkout Pro** (preference), não Bricks. | Reaproveitar só o cliente HTTP/assinatura; o fluxo de pagamento da loja é novo (Bricks + Payments API). Credenciais **por tenant** (cada loja tem sua conta MP): `access_token` (secreto), `public_key` (browser), `webhook_secret`. Fase 6: MP Connect (OAuth) para não copiar/colar token. |
| 3 | **`chat.muhbianco.com.br` já é o Muchat (Stoat via Caddy)**, definido em `/root/dynamic_conf.yaml`. | CRM fica em `chatwoot.muhbianco.com.br`. `chat.<tenant>` vira **redirect 302** para `chatwoot.muhbianco.com.br/app/accounts/{id}`: o Chatwoot tem um único `FRONTEND_URL`; hospedar o dashboard sob domínio do tenant quebra cookies/ActionCable. Se quiser reaproveitar `chat.muhbianco.com.br` para o CRM, é preciso mover o Muchat primeiro (decisão de negócio). |
| 4 | **Traefik v3.7 usa ACME HTTP-01** (`/root/traefik.yaml`), sem DNS-01, sem wildcard. Rotas nascem de labels Swarm (estáticas) ou do file provider `/root/dynamic_conf.yaml` (watch). Provedor DNS de `muhbianco.com.br` não está documentado. | Domínios de tenant são dinâmicos → adicionar **`providers.http`** no Traefik apontando para `GET https://api-commerce…/internal/edge/traefik`, que devolve routers/services só dos domínios **verificados**. Certificado por host via HTTP-01 (funciona para apex e subdomínio do cliente). Wildcard `*.loja.muhbianco.com.br` fica para quando houver API do DNS (DNS-01). |
| 5 | **Google OAuth** exige `redirect_uri` registrada; não dá para registrar cada `lunares.com.br`. | Callback **central** (`api-commerce.muhbianco.com.br/api/v1/auth/google/callback`) + `state` assinado com tenant e host de retorno + **código de handoff** de uso único que vira cookie de sessão **no domínio do tenant**. PKCE e nonce gerados e guardados server-side. |
| 6 | **Chatwoot**: branding do dashboard é da instalação (`LOGO`, `LOGO_DARK`, `LOGO_THUMBNAIL`, `BRAND_NAME` em `InstallationConfig`, editáveis no Super Admin e aceitam URL). Custom attributes são **por account** (`custom_attribute_definitions.account_id`, tipos `checkbox`, `list`, `link`…). Automations têm ação **Send Webhook Event**. **Dashboard Apps** (iframe com `appContext`: conversation, contact, currentAgent) existem. Platform API cria accounts/users. | Quase tudo que a loja precisa **não exige fork**: `liberar_loja` = contact attribute checkbox criado só nas accounts com loja ativa; atributos de pedido na conversation; painel "Pedido" = Dashboard App servido pelo nosso painel; provisionamento via Platform API. Logo do tenant no Chatwoot = avatar da inbox/portal (branding global é MuhBianco). Os SVGs do overlay atual podem sair do fork e virar URLs no MinIO. |
| 7 | **Repo `muh-chatwoot` atual é órfão**: 7 commits, `.gitignore *`, só 8 arquivos (Dockerfile `FROM chatwoot/chatwoot:v4.17.1`, stack, 2 overlays Ruby, 3 SVGs). Sem merge-base com upstream. O fork correto `muhbianco/muchatwoot` já existe (6.821 commits, `develop`). | Migrar as duas correções Ruby como commits reais sobre `v4.17.1` no fork (`mb/main`), manter Dockerfile overlay gerado a partir do `git diff` contra a tag, propor upstream o fix do `webhook_url = "null"`. Detalhe em [06](06-integracao-chatwoot.md). |
| 8 | **MariaDB 10.11 roda no host**, `bind 0.0.0.0:3306`, sem TLS. | Antes de criar `mucommerce`: restringir bind/firewall à bridge Docker e ao localhost. Dois usuários: `mucommerce_migrate` (DDL só em `mucommerce.*`, cria o database se não existir) e `mucommerce_app` (DML). Runtime nunca tem `CREATE`. |
| 9 | **Capacidade**: 8 vCPU / 16 GB, 41 containers, ~9 GB livres. | Orçamento da stack `commerce`: api 512 MB, worker 512 MB, beat 128 MB, web Next.js 512 MB (~1,7 GB). Observabilidade **leve** (agente único + SaaS gratuito) em vez de Loki/Tempo/Prometheus locais. Staging da loja cabe; staging do Chatwoot só sob demanda. |
| 10 | **Modo "expor agente" existiu** (commits `552b989`…`5bc304b`, 04–05/08/2026) sobre WuzAPI e foi removido em `4b61e01` (Cloud API) e depois YCloud (`bfe7cb4`). Estado ficava em `user_services.settings` (`wa_mode shared|owned`, wizard, grupos); pool em `shared_wa_numbers` (hoje `whatsapp_senders`). Stack do WuzAPI nunca esteve no repo (host externo `wuzapi.muhbianco.com.br`, DB `wuzapi` vazio no Postgres). | Não ressuscitar o código antigo: reimplementar `owned` como **provider** em `whatsapp_senders.provider ∈ {ycloud, wuzapi}` na `api-agents`, com stack WuzAPI própria em `infra/`, atrás de feature flag por tenant. Pedidos por agente passam pelo mesmo gate da `api-commerce` (fase 5). |
| 11 | **Reaproveitar a `api-agents` como backend da loja?** Ela é single-tenant (escopo `user_id`), mistura billing SaaS (`services`, `wallets`, `topups`), canais e LLM; recebe webhooks de latência crítica (YCloud/Meta). | **Recomendação: serviço novo `api-commerce`** no monorepo `mucommerce`, mesma convenção FastAPI (Router → Service → Repository → Model, Alembic, Celery), banco próprio. `api-agents` continua roteador de canais e chama a `api-commerce` pelo gate de venda interno. Justificativa completa em §3. |
| 12 | **Conciliação `liberar_loja`**: contatos criados pelo WhatsApp têm telefone e raramente e-mail; o login Google entrega e-mail verificado. | Chave dupla: e-mail normalizado **ou** telefone E.164 verificado por OTP (YCloud via `api-agents`). Fluxo "Solicitar acesso" cria/atualiza o contato no Chatwoot do tenant e abre conversa para o operador aprovar. Fonte da verdade do acesso = `customer_tenant_access` na `api-commerce`; Chatwoot é espelho bidirecional com proteção de eco. |
| 13 | **Chatwoot webhooks não têm replay** nem painel de entregas. | Nunca depender só do webhook: job de reconciliação lê a Application API (contatos com `liberar_loja`, conversas com `order_id`) e corrige divergências. |
| 14 | **Fiscal**: `api-agents` tem só NFS-e (serviços). Venda de mercadoria exige NF-e/NFC-e (SEFAZ estadual). | Fora do MVP; fase 6 via provedor (eNotas/Focus NFe/NFE.io). Modelo já guarda `tax_document_ref` no pedido. |
| 15 | **Eventos** (brownies, encomendas, agenda) misturam catálogo, capacidade e janela de venda. | Entidade `events` com `event_products` e `capacity`; ingresso vira `product.kind=ticket` no futuro sem quebrar o modelo. |

## 2. Arquitetura recomendada em poucas linhas

Monólito modular **FastAPI (`api-commerce`)** + workers **Celery/Redis**, banco **MariaDB `mucommerce`** compartilhado com `tenant_id` em toda linha e filtro automático de sessão, **Next.js** (App Router, SSR) servindo landing, vitrine, checkout, área do cliente e painel, **Traefik** com provider HTTP dinâmico para domínios de tenant e certificados HTTP-01 por host, **MinIO** para mídia, **Chatwoot** (fork `muchatwoot`, mudanças mínimas) como CRM via Application/Platform API + Dashboard App, **n8n** só como transporte de e-mail, **api-agents** como roteador de canais que consome o gate de venda da `api-commerce`. Eventos de domínio saem por **transactional outbox** para consumidores idempotentes.

## 3. Principais decisões (com justificativa curta)

| Decisão | Escolha | Por quê |
|---------|---------|---------|
| Backend | Serviço novo `api-commerce` (FastAPI 0.14x, SQLAlchemy 2 async, Alembic, Pydantic v2, Celery 5) | Bounded context próprio; deploy/rollback independente da `api-agents`; modelo `tenant_id` desde a primeira migration; menor raio de explosão em webhooks de pagamento. Alternativa (módulo dentro da `api-agents`) economizaria um container, mas herda modelo `user_id`, banco `api_agents` e cadência de deploy do roteador. |
| Frontend | Next.js (App Router, `output: standalone`), 1 container | SEO/OG por tenant com SSR, middleware lê `Host`, um só build para storefront + painel, SDK Bricks do MP roda no browser. |
| Multi-tenancy | Shared DB / shared schema + `tenant_id` + `with_loader_criteria` global + FKs compostas nos agregados críticos | Custo operacional mínimo no hel1; isolamento reforçado em 3 camadas (Host → contexto, filtro ORM automático, FK composta) + testes de vazamento. |
| Resolução de tenant | Só por `Host` (Traefik) ou `X-Tenant-Host` com token interno (Next → API); validado em `tenant_domains.status=active` | Sem `tenant_id` do navegador; Host inválido = 404. |
| Domínios/TLS | Traefik HTTP-01 por host + `providers.http` alimentado pela API | Sem trocar a borda; Caddy segue só no Muchat. |
| Fila/jobs | Celery + Redis (DB 3), queues por domínio, beat | Já operado no hel1 (`api-agents`); Dramatiq/Arq não trazem ganho que justifique um segundo runtime. |
| Eventos | Outbox transacional (`outbox_events`) + relay + `processed_events` por consumidor | Publicação confiável sem broker extra; consumidores idempotentes; DLQ na própria tabela. |
| Pagamentos | `PaymentProvider` com `MercadoPagoProvider` (embedded), `InfinitePayProvider` (redirect), `FakeProvider`; seleção por tenant | Cada tenant escolhe; webhooks sempre confirmados por consulta ativa; reconciliação periódica. |
| Chatwoot | Tenant = account; integração via Platform/Application API, custom attributes, webhooks, automations e **Dashboard App**; fork só com 2 fixes Ruby | Upgrades continuam possíveis; UX de avanço de status validada pela `api-commerce`. |
| Acesso à vitrine | Configurável por tenant (`public`, `login_required`, `whitelist`); MVP default `whitelist` | Atende Lunares hoje sem fechar as demais opções. |
| Custo | Custo médio ponderado móvel por insumo; snapshot de custo por item de pedido | Simples, auditável, não recalcula histórico. FIFO por lote opcional depois. |
| IDs / dinheiro / tempo | UUIDv7 `CHAR(36)`; centavos `BIGINT`; UTC + timezone por tenant | Ordenação temporal no InnoDB, sem float, sem ambiguidade de fuso. |
| Fiscal, frete, cupom, assinatura, marketplace | Fora do MVP, modelo preparado | Não bloqueiam a primeira loja. |

## 4. Principais riscos

| Risco | Mitigação |
|-------|-----------|
| Webhook InfinitePay forjado (sem assinatura) | Só marcar pago após `payment_check` com `handle`+`order_nsu`+`transaction_nsu`+`slug` e `paid_amount ≥ amount`; endpoint com segmento secreto por pagamento; dedupe por `transaction_nsu`. |
| Vazamento entre tenants | Filtro ORM global + FK composta + testes parametrizados (2 tenants × todos os endpoints) + revisão obrigatória de queries cruas. |
| Certificado não emitido (DNS errado, rate limit LE) | Domínio só entra no Traefik após verificação TXT+A/CNAME; job de `tls_status`; alerta; fallback no subdomínio `*.loja.muhbianco.com.br`. |
| Fork Chatwoot travar upgrade | Diff mínimo (2 arquivos), rebase por tag, CI com specs alvo, PR upstream do fix. |
| Duplicidade de pedido por retry de agente/webhook | `Idempotency-Key` obrigatório (site e agentes), unique `(tenant_id, idempotency_key)`, `processed_events`. |
| Estoque negativo / reserva presa | Ledger + saldo com lock de linha; TTL de reserva; job de expiração; reconciliação soma(movimentos) = saldo. |
| Host saturado | Limites de recurso na stack; observabilidade leve; staging Chatwoot só sob demanda. |
| Google consent screen mostra "MuhBianco" e não a marca do tenant | Comunicar; branding próprio por tenant exige app OAuth por tenant (fora do MVP). |
| Dependência do WuzAPI (não oficial: bloqueios, sem SLA) | Feature flag por tenant, isolamento em stack própria, termos de uso explícitos, canal oficial como padrão. |

## 5. MVP versus fases posteriores

**MVP (fases 0–3, primeira loja no ar):** tenancy por domínio, landing configurável, catálogo simples (produto + variante + estoque controlado), login Google + `liberar_loja`, carrinho, checkout Mercado Pago (Pix e cartão) **e** InfinitePay (redirect) selecionáveis por tenant, pedidos com máquina de estados, e-mails transacionais, Chatwoot (contato, conversa, atributos, Dashboard App de avanço), painel de ativação de tenant com provisionamento assíncrono, domínio custom com TLS, auditoria, outbox.

**Depois:** produção/insumos/receitas/custos (fase 4), agentes de venda + WuzAPI (fase 5), cupons, frete/logística, fiscal, MP Connect, analytics/LLM, assinatura, marketplace (fase 6+).
